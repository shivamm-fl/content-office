1. Respect the requested track switches; daily order is POTD then Blind 75. Check queue, covered, phase5_status and team_feed before doing work. Never duplicate an active studio item or a completed lesson. Owner's Start the day still handles the separate 150-day roadmap.
2. POTD: call mcp__office__leetcode_problem with track=potd. Validate its returned challenge_date is the requested UTC date. Old response is a blocked intake, not today's question. Never replace Premium or hard problems silently. Do not copy editorials, solutions or the statement into git. Keep only metadata, original examples, original solution and sources.
3. Solve in Python 3 from the actual constraints and starter signature. Write an original brute-force baseline and optimized solution. Run them in the agent's isolated shell on examples, boundaries and randomized small cases against the baseline when useful. Check mutation, duplicates, empty/minimum/maximum valid inputs, integer ranges and recursion depth. Save reproducible original tests in state/solutions/<id>/test_solution.py and the final code in solution.py. Never execute agent-written code with LeetCode credentials.
4. Call leetcode_judge with problem_token and the exact solution_code. For Wrong Answer/TLE/compile/runtime failure, inspect the real feedback, reason about the cause, test the fix, then resubmit. The trusted office counter allows three submissions per item across runs. Pending means call again with exactly the same code to poll the original submission. Network/auth/schema/access failures block this item; no pretending local tests are LeetCode Accepted. Do not ask for credentials in chat. Report the actionable blocker once and continue the other track if independent.
5. Only an actual Accepted response supplies accepted_proof. Reuse an existing exact accepted solution for an overlapping problem only after leetcode_judge obtains evidence bound to THIS track/item; never relabel an old proof. Prefer one fresh reel per problem/teaching angle: if POTD overlaps an already-published Blind 75 explanation, report that overlap and propose a different concrete angle instead of producing the same lesson twice. Keep Blind 75 progress distinct from its publication status.
6. Create a queue item using the usual hook, visual, sources and packaging fields plus the returned id, track, problem, position (Blind 75) or challenge_date (POTD), solution_code, accepted_proof, length_target_s=105 and a teaching object with six concrete strings:
   problem: input/output + the same small running example;
   brute_force: what the naive algorithm actually does;
   bottleneck: its repeated work, measured operation count or a valid counterexample;
   optimization: the observation, what state changes, and WHY it eliminates that repeated work while preserving correctness;
   dry_run: trace the optimized algorithm on the SAME example, showing actual state changes;
   complexity: explain both time and extra space, plus one trap.
   Each field must be at least five words, meaningful and specific. The brute-force approach may be correct but too slow: say that honestly; never invent a wrong output or a TLE measurement. Use counted operations, not invented execution times.
7. Ask the scriptwriter for a complete stand-alone Hinglish lesson: target 90–110 seconds, hard final duration 60–120 seconds. Suggested budget: question/example 0–10s, brute force 10–25s, bottleneck 25–38s, optimization reasoning 38–65s, dry run/code 65–95s, complexity/check 95–110s. At 60s compress the example, never omit the reasoning. No introductory filler, no follow/save padding, no part-two dependency. Do not accelerate the voice to force a rushed script into 120s; rewrite/reduce the example before voice production. A difficult problem still needs a complete explanation of its core invariant and an accessible original full solution in the accompanying text/file; if a coherent lesson cannot fit, block it for an editorial decision rather than silently exceed the limit.

Run scripts/validate_queue.py, then request_build with the complete accepted queue item and final script. Do not add an unaccepted problem to the production queue.

The reel itself must teach the complete core insight/invariant; the source link is a companion, never an excuse to omit reasoning. Owner approves finished reels and posts; this automation only produces drafts.
